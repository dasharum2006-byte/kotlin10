# Вывод по практической работе (Модуль 2, задание 10)

## Краткий вариант

В ходе работы были изучены жизненный цикл Activity и механизм рекомпозиции Jetpack Compose,
а также получены практические навыки поиска и исправления ошибок в декларативном UI.
С помощью логирования (класс `Log`, тег `MainActivity`, окно Logcat) удалось проследить
последовательность вызовов `onCreate → onStart → onResume → onPause → onStop → onDestroy`,
убедиться, что при повороте экрана Activity уничтожается и создаётся заново, и что
сохранение состояния должно выполняться через `Bundle` / `rememberSaveable`.
При исправлении приложения «Корзина онлайн-магазина» было установлено, что причиной
некорректного подсчёта суммы являлось вычисление итоговых значений (`totalSum`, `productSize`)
прямо в теле composable-функции: тело композиции может выполняться многократно, поэтому
побочные эффекты в нём недопустимы. В исправленном варианте сумма и количество товаров
вычисляются из единственного источника правды (`Cart.products`), вызов `Toast` перенесён
в `LaunchedEffect`, а состояние корзины хранится в `rememberSaveable`.
Основной вывод: composable-функции должны быть идемпотентными и зависеть только от явных
параметров, состояние — храниться в одном месте (`remember`/`rememberSaveable`), а побочные
действия — выполняться в эффектах или обработчиках событий. Такой подход исключает лишние
рекомпозиции, обеспечивает предсказуемое поведение интерфейса и сохранение данных
пользователя при изменениях конфигурации.

## Подробный вариант (с разбивкой по частям)

**По части I (жизненный цикл Activity).** Были рассмотрены основные состояния Activity
(created, started, resumed, paused, stopped, destroyed) и соответствующие им методы
обратного вызова. Практика показала, что переходы не всегда линейны: при частичном
перекрытии экрана вызывается только `onPause()` без `onStop()`, при возврате в приложение
после остановки — `onRestart() → onStart() → onResume()`, а при изменении конфигурации
Activity уничтожается и создаётся заново. Для анализа переходов удобно использовать
логирование: константа `TAG` с именем класса позволяет фильтровать сообщения в Logcat
по тегу и уровню (`Log.d`, `Log.i`, `Log.w`, `Log.e`). Отсюда практический вывод: ресурсы
нужно освобождать в `onStop()`, а `onPause()` должен оставаться лёгким, так как задерживает
отображение следующих экранов. Данные, которые должны пережить пересоздание Activity,
сохраняются в `Bundle` в минимальном объёме.

**По части II (рекомпозиция).** Рекомпозиция — повторный вызов composable-функции при
изменении `MutableState` или входных аргументов. Compose сам определяет, какие узлы дерева
нужно обновить, поэтому функции должны быть идемпотентными и использовать только явные
аргументы, без обращения к глобальным и изменяемым внешним переменным. `remember`
сохраняет значение между рекомпозициями, но не при смене конфигурации; для второго случая
используется `rememberSaveable`. Инструмент Layout Inspector позволяет визуально увидеть,
какие composable-функции были перерисованы.

**По части III (практическое задание).** В исходном коде были выявлены ошибки:
1) накопление суммы и количества товаров в полях класса внутри тела композиции
(`totalSum += product.price`) — значения увеличивались при каждой рекомпозиции, из-за чего
итоговая сумма становилась больше реальной стоимости товаров;
2) вызов `Toast` непосредственно в composable-функции — побочный эффект в композиции
приводил к дублированию сообщений;
3) хранение состояния через `remember` — корзина терялась при повороте устройства;
4) формирование `id` нового товара как `products.size` — после удаления товара ключи
дублировались;
5) отсутствие чёткого разделения на идемпотентные компоненты с явными параметрами.
После исправления сумма и количество товаров вычисляются из списка товаров
(`sumOf`, `size`), сообщение о бесплатной доставке показывается в `LaunchedEffect` при
превышении порога 500, корзина хранится в `rememberSaveable` с собственным `Saver`,
уникальность `id` обеспечена через максимальный существующий идентификатор, а интерфейс
разделён на независимые composable-функции. Приложение корректно добавляет и удаляет
товары (кнопка удаления отображается только при непустой корзине), правильно считает сумму
и сохраняет состояние при повороте экрана.

**Общий вывод.** Декларативный подход Compose требует дисциплины в работе с состоянием:
единственный источник правды, отсутствие побочных эффектов в композиции, идемпотентные
composable-функции и правильный выбор между `remember` и `rememberSaveable`. Соблюдение
этих правил устраняет целый класс ошибок «неверных вычислений» и «пропадающих данных»
и делает поведение приложения предсказуемым при любых изменениях жизненного цикла.
